- Notas: Follow Red, Green, Refactor with one focused regression path and run only the affected Java tests before the mandatory feature gates. Bounded context: Transaction hands an opaque checkout fact to Inventory, which hands it to Payment through versioned integration events. Use case: start a Card checkout and request its real Mercado Pago authorization asynchronously. Aggregate: Transaction and InventoryReservation preserve their existing lifecycle invariants; the short-lived provider token is transport metadata, not a business decision or raw Card datum. Invariants: the checkout operation key remains bound to the token through the existing semantic hash; Card requires both the token and payment method identifier; Pix carries neither; the exact values reach Payment without derivation or hard-coding; PAN, CVV, expiry, access tokens, and reusable credentials remain forbidden. Consistency boundary: the existing Transaction and Inventory event/outbox commits, with the short-lived token durably carried only as required for redelivery. Affected ports: TransactionOutbox and InventoryOutbox; public GraphQL and Mercado Pago provider contracts remain unchanged. This narrowly supersedes the older T-248 note forbidding every provider credential in Transaction events: AC-161 already permits the single-use, short-lived provider token across RabbitMQ and persistence, while reusable credentials remain prohibited.
