# T-185 — Better Auth lifecycle, registration, and resource scopes

## Investigation and decisions

The workspace pins Better Auth, its OAuth provider, and
`@thallesp/nestjs-better-auth` at 1.7.1, 1.7.1, and 2.7.0 respectively. The
installed Nest integration supports `AuthModule.forRootAsync`, provides
`AuthService`, and discovers injectable hook classes decorated with `@Hook`
and `@AfterHook` when the Better Auth instance has `hooks: {}`. The resulting
module keeps the existing integration and replaces manual decorator calls with
normal Nest decorators and explicit injection tokens. Explicit tokens are
required by the project's `tsx` test runtime because it does not emit
`design:paramtypes`.

The private provider module remains necessary: an imported dynamic module can
inject an exported token from one of its own imports, but it cannot inject a
provider declared later by the module that imports it. It has no runtime or
security cost beyond the normal Nest provider graph. The public
`BetterAuthModule` owns the hook, bootstrap provider, and controller.

Better Auth remains the sole owner of users, accounts, sessions, and OAuth
records. Registration only uses Better Auth's `internalAdapter` during the
documented hook callback; this task adds no ORM entity or second user mapping.
The WordPress custom provider is a standard Nest factory provider for an
external system.

The installed OAuth provider 1.7.1 implementation documents and performs a
sequential intersection of requested scopes with every requested resource's
`allowedScopes`. The existing E2E flow deliberately requests one token for all
five audiences and forwards that token to the owning resource servers. Giving
those resources disjoint lists would remove valid delegated scopes or produce
`invalid_scope`. The five-resource issuance contract therefore retains one
shared set named `DELEGATED_OAUTH_SCOPES`. Every value corresponds to a current
protected operation (`mcp:tools`, `marketplace:read`, `cart:read`,
`orders:read`, or `cart:write`), while the existing resolver, MCP, workflow,
and Spring Security guards enforce the scope needed by each operation. The
misleading `MCP_TOOL_SCOPES` alias was removed.

## Red

Before editing production files, the focused regression command was:

```sh
corepack pnpm@10.17.1 exec vitest run \
  libs/identity/nest/src/auth/better-auth.factory.spec.ts \
  libs/identity/nest/src/auth/registration.service.spec.ts \
  --reporter=verbose
```

It produced 7 expected assertion failures and 6 passes. The failures proved
that registration did not delete the customer created by the failing attempt,
cleanup stopped after the first rejection, cleanup failures had no typed
details, PostgreSQL disabled certificate validation, existing OAuth clients
still required a seed password, concurrent bootstrap was not coalesced,
unready clients raised an untyped error, and multiple `Set-Cookie` values were
not converted to a valid request `Cookie` header. The old bootstrap also
emitted expected unhandled database/password rejections after those failed
assertions; Green removed that source of background work.

## Green and refactor

The minimum behavior was implemented and then refactored around standard Nest
providers:

- `IdentityDatabasePool` lazily owns one internal pool, verifies production
  certificates by default, permits the explicit `DATABASE_SSL=false` override,
  and closes the pool once through `onModuleDestroy`.
- `IdentityAuthBootstrap` coalesces concurrent startup, skips password access
  for existing clients, repairs missing resource links, publishes client IDs
  only after both seeds succeed, and can retry after failure.
- Identity errors now carry stable typed codes. Registration compensation
  retains the original failure, records each cleanup failure, and continues
  every independent cleanup step.
- WordPress rollback receives only the ID returned by this attempt's successful
  create call. Pre-existing and raced accounts fail before that ID is assigned
  and are never deleted.
- A real Nest `TestingModule` resolves the auth service, hook provider,
  bootstrap dependency, and OAuth client controller.
